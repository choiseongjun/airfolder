# Originals and compressed playback

The application accepts videos up to 50 MiB and images up to 20 MiB. Admission is capped at 500 MiB per viewer and 5 GiB across the service, including originals and previews. Pending previews reserve at least the original size or 1 MiB. Legacy preview sizes are conservatively estimated when missing. Existing media is retained when limits are exceeded; new uploads are rejected. These are storage admission caps, not a billing or bandwidth ceiling. The effective limit is the lower of this limit and the private Supabase bucket limit. `/api/media-limits` returns the effective limits. On 2026-10-14 the existing Pro project global limit was raised from 50 MB to 2 GB, and the private bucket limit was raised to 2 GiB. The spend cap remains enabled.

1. The historical storage configuration allows 2 GiB files, but application admission now enforces the lower limits above. Do not increase provider limits for this release. A Free project cannot exceed 50 MB; upgrading a paid plan and changing the global limit are account-owner operations. Other applications share this project, so preserve their individual bucket limits.
2. Run `node scripts/setup-server.mjs` to apply migration 009 and configure only `snaproom-photos` to 2 GiB. Setup deliberately fails rather than claiming success when the provider rejects the new limit.
3. `npm run dev` starts both the web server and media worker locally. In production, run `npm run media:worker` as a supervised, persistent Node worker, with the same database/storage environment as the web server. `node scripts/process-media.mjs --once` drains due jobs and exits. Install the platform's `ffmpeg-static` binary, or supply `FFMPEG_PATH` for an externally managed FFmpeg executable.
4. Deploy the upload route on a persistent Node server with writable temporary disk, a reverse proxy body limit allowing 50 MiB plus multipart overhead, and an upload timeout appropriate for slow mobile connections. A serverless host with a small request-body or execution-time cap will not support this route. Budget at least original size plus output size in temporary disk per active worker, and original size per simultaneous upload. Configure upload concurrency and disk monitoring in the deployment. This implementation streams multipart requests, but an interrupted upload restarts the file; it is not a resumable TUS implementation.

The selected original is stored byte-for-byte in the private bucket. Image previews are rotated/resized to at most 2560 px and encoded as JPEG quality 85. The persistent worker encodes video previews as MP4 H.264 / AAC, at most 1280 px on the long edge, CRF 28, capped video bitrate 2.5 Mbps, AAC 96 kbps, faststart enabled. Preview metadata is stripped; original metadata remains in the download. Very small or already optimized originals may be smaller than their normalized preview.

Default content requests serve only the preview for new original-backed media. While processing or after failure they return 425 and the UI displays a preview status. Explicit `?download=1` always streams the original; it does not buffer a multi-GB download in browser JS. Both paths enforce the same folder and audience permissions. Legacy entries without an original continue to expose the stored copy.

Jobs persist on the photo record, are protected by a PostgreSQL session advisory lock, and recover after a 65-minute lease if the worker crashes. FFmpeg is limited to 2 threads and 60 minutes per job. Failed jobs retry up to three times; original downloads remain available. Operators can retry a diagnosed failed job by setting its `preview_status='pending'`, `preview_attempts=0`, and `preview_retry_at=now()`. A failed encode must never replace or delete an original.

Validate with `npm test` and `node scripts/test-media.mjs`. The integration test covers byte-identical original downloads, distinct MP4 previews, processing-state behavior, byte ranges, and recipient authorization. The streaming test writes and verifies a 64 MiB multipart upload locally. Run `node scripts/test-storage-quota.mjs` for quota and concurrent-admission checks. Upload fixtures must respect the current 50 MiB video cap. Validate on the eventual production host and physical devices before release.
